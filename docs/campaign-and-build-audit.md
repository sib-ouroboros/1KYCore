# Аудит объектов кампаний и предупреждений сборки

Дата: 1 октября 2026. Ветка `development/character-tools`, проверенный commit
`948ebadf8a0b08b2e25b463b3e1db5dfd1c15123`. Это первый этап разбора: инвентаризация,
источник восстановления и приоритеты. Действующая БД и игровой C++ этим отчётом
не меняются; новые SQL ещё не включены в автоматический updater.

### Что нельзя потерять при переносе

- `faction`/`flags`/золото/WorldEffectID в нашей схеме находятся отдельно,
  в `gameobject_template_addon`. У кандидатов 66 ненулевых flags,
  8 faction и один WorldEffectID. Их нельзя молча отбросить.
- Шесть `questItemN` исходника должны преобразоваться в строки
  `gameobject_questitem`; ненулевой первый предмет есть у одного кандидата.
- Пять кандидатов имеют ненулевой SpellVisualID; такого столбца в нашей таблице
  шаблонов нет. Нужен разбор поддерживаемого ядром пути визуальных данных,
  а не произвольное расширение таблицы.
- Пустые AIName/ScriptName не отменяют проверки spell/loot/page/lock ссылок DataN,
  displayId в реальных DB2, фаз и карт. VerifiedBuild у отдельных записей равен
  1 или старому build: имя архива 26972 само по себе не доказывает игровую приёмку.
- В исходном архиве есть испорченные кодировкой названия (например, entry 240351).
  Реестр сохраняет исходный текст для аудита; такие имена нельзя считать готовой
  русской локализацией и молча переносить как исправленные.
- Прямых ссылок Type=2 в проверенных quest_objectives и связей
  gameobject_queststarter/ender на эти entry в дампе/37 SQL не найдено. Это не
  доказывает, что объекты декоративные: возможны spell, loot и сценарные связи.

Перед восстановлением можно выполнить только чтение:
[campaign-template-status.sql](../contrib/audit/campaign-template-status.sql).
Первый запрос проверяет живую таблицу спавнов; после нашей очистки там может быть
ноль невалидных объектов. Следующий запрос отдельно проверяет наличие 163
ожидаемых шаблонов: отсутствие спавнов не доказывает, что контент восстановлен.

### Последовательность восстановления

1. Проверить фактический результат обновлений в одноразовой БД и зависимости
   каждого типа. Отдельно начать с простых generic-шаблонов без ненулевых
   специальных полей; функциональные spellcaster/trap/chest/goober оставить
   отдельными проверяемыми группами.
2. Выпустить **новую** SQL-миграцию: точные шаблоны из указанного архива,
   необходимые addon/questitem записи и точные GUID/entry спавнов из реестра.
   Старую уже опубликованную миграцию не редактировать.
3. До любых изменений проверить GUID на конфликт с другим entry; существующие
   пользовательские шаблоны/спавны не перезаписывать без отдельного разбора.
4. Проверить первый импорт, повтор, частичное выполнение, сохранность посторонних
   записей, затем загрузку мира и взаимодействия в клиенте. По одному лишь
   наличию шаблона нельзя объявлять кампанию проходимой.

## Предупреждения: объём и смысл

В полных логах найдено **9588 сообщений**: GCC 3858, Clang 3524, Windows 2206.
Это число сообщений компиляторов, а не уникальных ошибок: одни заголовки
компилируются многократно, одна проблема появляется в нескольких сборках.
Ни один класс предупреждений не исключён из таблицы ниже. Для опасных сообщений
ниже отдельно прочитан исходный код; прочтение каждой строки каждого сценария
для остальных тысяч сообщений этим этапом не заявляется.

### Остальные группы

- Неиспользуемые параметры/переменные, отсутствие override, лишние const,
  устаревшие OpenSSL API, неизвестные GCC pragma в MSVC чаще дают шум сборки
  или риск совместимости с будущей библиотекой. Их массовое удаление не является
  исправлением игрового AI.
- Порядок инициализации, signed/unsigned, незаполненные enum-switch,
  fallthrough, подозрительные скобки/отступы, пустые тела и копирование
  объектов через memset требуют чтения конкретной логики. Их нельзя все
  признать безопасными только по названию категории.
- TC_LOG_* использует типизированный fmt::sprintf. Его неисполняемый
  check_args с ATTR_PRINTF сравнивает аргументы по правилам обычного C printf:
  часть сообщений о std::string_view/size_t здесь относится к этой проверке,
  а не к выполнению небезопасного printf. Проверять фактический formatter и
  возможную потерю ширины числа отдельно. Настоящий sprintf в vmap-инструменте
  этим объяснением не покрывается.
- WITH_WARNINGS_AS_ERRORS передаётся в CI, но CMake сообщает, что параметр
  не использован. Успех полной сборки не означает режима «warnings = errors».
  Строгий UBSan включён в регрессионных harness, а не во всём игровом сервере.

первично не аварийная категория, но это не доказательство безопасности каждого
