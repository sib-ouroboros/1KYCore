## Подтверждённое исправление диагностики

`SMART_EVENT_VICTIM_CASTING` проверяет третий параметр (Spell ID), но раньше выводил
первый параметр (cooldown). Исправлено только поле в ERROR-сообщении. Пример:
NPC 120808/event 3 в `Tomb of Sargeras.sql`: cooldown 5000–8000, spell filter 20000,
cast action spell 241027. Старое сообщение ошибочно называло 5000 Spell ID.
Это не исправление самого повреждённого события. Подмены спеллов и снятия validation нет.
Следующий лог должен иметь те же отказы, но корректные ID; сравнивать только номера из
старого сообщения нельзя. Фокусный тест проверяет реальные ветки валидатора, wildcard 0,
валидный спелл, неверный min/max и неверный Spell ID при разных cooldown.

## P0 и порядок завершения

Падение подтверждено логом, точный invalid access и владелец пока не установлены.
В текущем Main.cpp порядок: остановка io threads; OnShutdown; затем RAII при return —
CLI join, сеть/сессии, SOAP/RA, battlegrounds/instance saves/OutdoorPvP/maps,
ScriptMgr и ScriptReloadMgr, metrics, realm list, DB pools, OpenSSL.
Позже работают статические singleton-деструкторы. Это карта расследования, не диагноз.

Отдельная статическая проблема: StartDB открывает пять pools, а StopDB явно закрывает
только Character/World/Login перед MySQL::Library_End; Hotfix/Shop остаются для последующих
деструкторов. Возможная связь с crash требует GDB/ASan; исправление P0 на этом предположении
не заявлено. Нужно также проверить очереди отложенного удаления dynamic script modules.

На этом Windows-компьютере WSL-дистрибутив не установлен; Linux GDB/core dump в приложении
нет. Предоставленные локальные DB2 имеют build 26654, не подтверждённый набор 26972.
Полный Linux bootstrap и sanitizer shutdown здесь не выполнены.
Подготовлены две изолированные CI сборки и probe; инструкция — `worldserver-bootstrap-repro.md`.
