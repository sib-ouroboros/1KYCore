# Определение специализации для панели управления

При входе CharacterHandler передаёт OnlineMgr поле talent. Ранее FindPlayerTalentType
считал очки по трём старым страницам, но подсчёт был закомментирован, поэтому результат
всегда был 0. Теперь функция читает активный GetSpecializationId и соответствующую
запись ChrSpecialization, возвращая её OrderIndex (0..3), а не ID специализации.

Проверяются принадлежность классу игрока, отсутствие специализации питомца и диапазон
индекса. Отсутствующие/некорректные данные дают 255 — существующий маркер неизвестного
значения uint8 в OnlineMgr. Четвёртая специализация друида корректно определяется
для отчёта о входе. Выбор специализации самим игроком этим не изменяется.

Регрессионный тест компилирует фактическое тело функции с тестовыми Player/DB2:
четыре индекса друида, второй индекс охотника на демонов, изменение текущего ID,
неизвестный ID, отсутствие выбора, null, чужой класс, питомец и недопустимые индексы.
Это проверка логики поиска и валидации, не загрузка реальных DB2 и не тест клиента.

## Команда подготовки персонажа

`player_change` сохраняет прежний формат JSON и индексы `talent: 0`, `1`, `2`.
Теперь `talent: 3` выбирает четвёртую специализацию друида. Ранее команда это
значение отклоняла, поэтому допустимые старые сетевые запросы не меняют значения.
`talent: 255` означает «сохранить текущую специализацию»; этот же именованный
маркер PLAYER_SPECIALIZATION_KEEP используется как значение по умолчанию C++ API.
Внешние C++ вызовы, явно передававшие 3 для сохранения, должны перейти на маркер.
Внутри дерева таких вызовов нет. Отсутствующее поле talent по-прежнему означает 0.

До изменения уровня проверяется реальная запись DB2 для класса. Например, третий
индекс охотника на демонов и четвёртый индекс недруида отклоняются. KEEP при
отсутствующей/невалидной текущей специализации также отклоняется. Повторный запрос
во время незавершённой подготовки не перезапускает её. Смена проходит штатно через
ActivateTalentGroup; прямой записи поля специализации нет.

Предметы выбираются по фактически активной специализации и CanUseItem. Вместо
двух случайных попыток проверяются все кандидаты уровня; затем допускается переход
к более низкому уровню. Приоритет tenacity и исключение уже выбранного предмета
сохранены. При отсутствии совместимого предмета неподходящий не выдаётся.
Старые классовые наборы оружия остаются отдельным ограничением этого генератора;
фильтр не гарантирует заполнение всех слотов при неполной базе предметов.

Команда по-прежнему выполняет полную административную подготовку: уровень, таланты,
заклинания, очистку содержимого сумок и экипировку. Это не обычная смена специализации
игроком. Успешный ответ означает принятие запроса, выполнение идёт по шагам в UpdateReset.

Тест test_specialization_command.py компилирует реальные тела сброса, активации и
подбора предметов с тестовыми DB2/Player. Проверяются четыре специализации друида,
KEEP, некорректные индексы/классы/DB2, отсутствие изменения при отказе, повторный
запрос, фильтр экипировки и запасной поиск. Это не игровое испытание настоящих DB2.

## Оставшиеся отдельные вопросы

- OnlineMgr обновляет поле при входе; немедленное обновление панели без нового входа
  требует отдельной проверки уведомлений.
- Старый пустой кэш classesTalents больше не нужен для определения специализации.
- Старые классовые списки оружия требуют дальнейшей проверки для всех классов Legion;
  обычное ручное экипирование игрока этой командой не изменяется.
