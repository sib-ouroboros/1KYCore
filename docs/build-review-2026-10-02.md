## Исправленная ошибка Магни

В boss_aggramar.cpp обработчик NPC128169 передавал `TeleportTo(4000,1712,x,y,z,o)`. В актуальном Player.h сигнатура начинается с mapid,x,y,z,orientation,options: карта4000 не существует в предоставленной DB2, а последнее число превращалось в нулевой uint32 options. Карта1712 есть. Это реальная ошибка аргументов, а не безвредное округление float.

Вызов заменён на принадлежащее игроку BasicEvent через рабочую m_Events. Кинематографический Spell254311 вызывается как раньше; спустя4000мс выполняется TeleportTo(1712,2826.39,-4567.94,291.95,0.02513274) со штатными options0. При очистке событий/уничтожении игрока событие удаляется без выполнения. Изменение телепорта ограничено этим обработчиком. В release ScriptName NPC128169 уже задан; базовый npcflag0, поэтому доступность диалога после нужного этапа рейда требует отдельной игровой проверки.

Новый тест компилирует реальные обработчик и EventProcessor.cpp вместе с реальной декларацией TeleportTo из Player.h, используя строгие предупреждения и ASan/UBSan/float-cast-overflow. Проверяются граница3999/4000мс, исходные координаты/направление, независимые игроки, однократное выполнение и отмена/уничтожение владельца. Тест подключён к Reliability regression. Локального C++-компилятора нет; результат исполнения требуется проверить в Actions после публикации. Просмотр ролика и реальное перемещение клиента отдельно не подтверждены.

## Границы спавнов Агграмара

При чтении соседнего кода найден реальный выход за границы: LoadNPC использовал while(data->event), а массив spawnData содержит ровно4 строки и не содержит нулевой завершающей строки. Оба вызова из DamageTaken проходили за концом массива после своих двух спавнов.

Метод теперь перебирает фактический массив и фильтрует строки по событию; обе точки вызова используют этот ограниченный метод. В двух строках явно указано прежнее нулевое направление, раньше получавшееся из инициализации агрегата. Тип вызова SummonCreature, продолжительность, NPC, координаты, состав по два актёра на фазу и условия переходов не изменены. Проверка actual production table/method с ASan/UBSan добавлена для обеих фаз, неподходящих событий и повторного вызова. Полная корректность всей механики боя этим тестом не утверждается.

## Выявленная проблема отложенных функций

Unit::AddDelayedEvent складывает функции в m_Functions, а EventProcessor::AddFunction — в m_functions_queue. В текущем коде нет обновления m_Functions или исполнения этой очереди; Unit::Update обрабатывает m_Events и _scheduler. Аналогичные поля присутствуют у Group/GroupMgr. Например, Creature::SetReactState с задержкой использует этот путь.

Это унаследовано от базового f8fcb8ad38f52f0a0e7e4dbfde0c64a6b4b04932: повторно прочитаны EventProcessor.cpp, Unit.cpp и Unit.h той версии. Удаление ботов эту очередь не отключало. GameObject имеет отдельный работающий AddDelayedEvent через m_Events. Поэтому для исправления Магни использована рабочая BasicEvent, а общий scheduler не изменён.

Следующий приоритетный разбор: восстановить исполнение отложенных функций после проверки всех захватов указателей, отмены при сбросе/выходе, боевых условий и владельца очереди. Простое включение всех накопленных callback может активировать старые сценарии с небезопасными ссылками; требуется отдельная регрессия и аудит используемых NPC/групповых обработчиков.
