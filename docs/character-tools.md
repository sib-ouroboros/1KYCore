# Команды управления персонажами

Ветка разработки: `development/character-tools`. Клиент игры: Legion 7.3.5 (26972).
Это протокол существующего административного ToolSocket. Сохраняются разрешённые
IP, авторизация и формат кадра: двухбайтовая длина, JSON и завершающий NUL.

## Смена специализации без подготовки

```json
{"entry":"player_specialization","guid":123,"talent":3}
```

`guid` — ID **аккаунта**, как в прежней команде `player_change`.
`talent` обязателен: индекс DB2 `0–3` или `255` (оставить текущую).
Четвёртая специализация доступна только классу, у которого она действительно есть.
Сервер вызывает штатный `ActivateTalentGroup`, отправляет таланты и сохраняет
персонажа. Команда не меняет уровень, не сбрасывает выбранные таланты, не выдаёт
экипировку и не удаляет предметы. Штатные действия ядра при смене специализации
(ауры, питомец, панели действий, несовместимое оружие) сохраняются.

Нужен персонаж онлайн, от 10 уровня, живой, вне боя, полёта, телепортации,
торговли и поля боя/очереди. Ожидающая подготовка блокирует другую операцию.
Ответ `result: "success"` означает, что штатная смена выполнена и сохранение
передано в БД; `error` — отказ.

## Полная административная подготовка

```json
{"entry":"player_change","guid":123,"minlv":110,"maxlv":110,"talent":255}
```

Совместимость существующего запроса сохранена: если `talent` отсутствует,
используется индекс `0`. Успешный немедленный ответ означает **принятие** запроса.
Уровень и XP до начала выполнения не изменяются. Все шаги подготовки выполняются
за один вызов обновления игрока. Ожидающая операция также завершается перед
сохранением/удалением игрока при выходе, отключении или штатной остановке сервера.
`Player::SaveToDB` откладывает промежуточные сохранения до последнего шага.

Подготовка по-прежнему меняет таланты, заклинания и экипировку: для обычной смены
специализации используйте предыдущую команду. Удаление предметов из рюкзака
убрано полностью. Старые вещи сохраняются; при замене экипировки они перемещаются
штатными проверками ядра. При нехватке места подготовка может выдать лишь часть
новых вещей, а результат будет содержать предупреждения. Неудачно экипированный
новый предмет остаётся в инвентаре. Команда не гарантирует наличие всех нужных
шаблонов в конкретной БД/DB2.

## Результат отдельно от принятия

```json
{"entry":"player_change_status","guid":123}
```

Пример ответа:

```json
{
  "entry":"player_change_status",
  "guid":123,
  "result":"success",
  "operation":{
    "id":42,
    "character_guid":456,
    "kind":"preparation",
    "state":"completed_with_warnings",
    "item_failures":2
  }
}
```

Состояния подготовки: `queued`, `running`, `completed`,
`completed_with_warnings`. Смена специализации: `running`, `completed`, `rejected`.
`item_failures` — число обнаруженных сбоев создания/размещения/экипировки;
это не перечень всех отсутствующих предметов и не число повторных попыток.
`operation: null` означает, что операций ещё не было. Неизвестный аккаунт
возвращает `result: "error"`. Последний результат доступен после выхода персонажа;
`character_guid` позволяет отличить его от другого персонажа того же аккаунта.
Поле `operation` также добавляется к записи аккаунта в `player_acc`.

Статус хранится в памяти, ID операции действует только до перезапуска процесса.
`completed` означает завершение шагов и передачу итогового сохранения в БД,
а не подтверждение асинхронного commit БД. Защита выхода и штатного перезапуска
не заменяет журнал восстановления после аварии: при принудительном завершении
процесса, отказе БД или питания атомарное восстановление всех побочных записей
штатных методов не гарантируется. До начала выполнения запрос безопасно теряется
без изменения персонажа; автоматического повторения запроса после запуска нет.

## Список аккаунтов по страницам

```json
{"entry":"player_acc","after":0,"limit":100}
```

Ответ сохраняет `entry`, `result`, `accounts` и добавляет `total`, `after`,
`limit`, `next_after`, `has_more`. Аккаунты идут по возрастанию ID, только строго
после `after`. Для следующей страницы передавайте полученный `next_after`;
завершайте при `has_more: false`. Курсор — не номер страницы и не смещение.
`after` допускает весь диапазон uint32; `limit` — `1–100`.
Старый запрос без параметров возвращает первую страницу до 99 записей.

Размер страницы дополнительно ограничен примерно 60 КБ, чтобы ответ помещался
в существующий кадр. Страница может содержать меньше `limit` записей:
продолжение всё равно определяется курсором. Одна чрезмерно большая запись
возвращает `error: "account_too_large"`; такой запрос нельзя бесконечно повторять.
Список отражает текущее состояние, а не снимок: добавленный во время обхода
аккаунт с уже пройденным ID будет виден при следующем полном обновлении.

Исходников внешней панели в проекте нет. Для работы её интерфейса нужно подключить
новую команду специализации, опрос статуса после принятия подготовки и цикл
страниц. Старый интерфейс продолжит получать прежние ответы, но самостоятельно
не начнёт запрашивать следующие страницы.

## Проверки

Регрессионные тесты компилируют реальные тела изменённых функций с тестовыми
Player/DB2 и настоящим JsonCpp: отдельная специализация, отложенная мутация,
блокировка промежуточного сохранения, завершение перед выходом, сохранность вещей,
предупреждения, идентичность операции, 251 аккаунт и ограничение размера страниц.
В CI используются ASan/UBSan и полные сборки GCC, Clang и Windows.
Игровая приёмка с реальными DB2, выходом/перезапуском и заполненными сумками нужна
перед внедрением на рабочий сервер.
